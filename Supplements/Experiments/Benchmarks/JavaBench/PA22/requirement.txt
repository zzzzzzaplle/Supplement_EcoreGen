1. Overview

This project implements a multi-player variant of the classic grid-based puzzle game Sokoban. The core mechanic involves players moving around a closed-boundary map to push boxes to specific destinations. This variant supports multiple players, up to 26, and each player can only push the boxes assigned to them. The objective is to navigate the board and place all boxes onto the designated destinations. The game also includes customizable undo quotas, action validation, and a terminal-based text user interface.

2. Functional Requirement

The system manages two-dimensional grid coordinates through the Position class. The game board is represented by GameMap, which is initialized from a text-based map representation. The first line of the input defines the undo limit. The symbol # represents a Wall, . represents an Empty space, @ represents a destination whose underlying entity is Empty, upper-case letters represent Players, and lower-case letters represent Boxes. Player IDs are represented by letters, where A corresponds to player 0, B corresponds to player 1, and so on. Each lower-case box belongs to the player with the corresponding upper-case letter, such as a belonging to A and b belonging to B.

The map must satisfy several validation rules. The undo limit must be -1 for unlimited undo or a non-negative integer; values smaller than -1 are invalid. The map must have a closed boundary, meaning the outer boundary must block movement. There must be at least one Player, and the same Player ID must not appear more than once. The number of destinations must be equal to the number of Boxes. Every Box must reference a valid Player ID that exists in the map, and every Player in the map must have at least one corresponding Box.

The dynamic game state is handled by GameState, which keeps track of entities and destination positions. During Move actions, including Up, Down, Left, and Right, the initiating player attempts to move from the current Position to a nextPosition. A Player can move into an Empty space or push a Box. A Box can only be pushed if its playerId matches the initiating Player's ID and the position behind the Box is empty. Movement is blocked by Walls, other Players, or Boxes that cannot be pushed.

Each processed action must return an ActionResult, either Success or Failed with a reason. The game also supports an Exit action. When an Exit action is processed, the game records an internal exit state so that the main game loop terminates. The game loop must also terminate when the current GameState satisfies the win condition. The game is won when every destination position is currently occupied by a Box.

The terminal input rules are case-insensitive. Player 0 uses W for up, A for left, S for down, and D for right. Player 1 uses K for up, H for left, J for down, and L for right. R triggers an Undo action with initiator 0, and U triggers an Undo action with initiator 1. The commands exit and quit trigger an Exit action with initiator -1. Any other input returns an InvalidInput action with initiator -1.

TerminalSokobanGame is the main runner extending AbstractSokobanGame and coordinating the terminal game loop. Although the backend supports up to 26 players, the terminal interface supports at most two players. If the supplied GameState contains more than two players, TerminalSokobanGame must reject it with an IllegalArgumentException. The terminal game renders the initial board state before entering the loop, then repeatedly reads one action from TerminalInputEngine, processes the action, prints the corresponding message through TerminalRenderingEngine, and renders the updated state.

TerminalInputEngine is responsible for reading user commands from the input source. TerminalRenderingEngine is responsible for rendering the game grid to the output stream. The rendered board must use the following character representations: Wall is displayed as #, Box is displayed as a lower-case letter based on playerId, Player is displayed as an upper-case letter based on playerId, an Empty cell that is also a destination is displayed as @, and other Empty spaces are displayed as .. The message output prints the given content string to the output stream followed by a newline.

The game provides an Undo mechanism. Transitions are accumulated during movement, and a checkpoint is recorded when a Box is successfully pushed. Checkpoints are stored in the history stack of GameState. When an Undo action is executed, the game reverts the state using the transition and checkpoint history. Undo transitions must be applied atomically to preserve the correct final state of all entities. The undoQuota uses 0 to indicate that undo is not allowed and -1 to indicate unlimited undo. A finite undo quota is consumed only when there is a checkpoint in history that can actually be undone.

3. External Utilities and Known Information

SokobanGameFactory and Sokoban are the entry points that load map files, create the game map, and initialize the game engines. StringResources is a utility class that centralizes display messages and prompts, such as WIN_MESSAGE, INVALID_INPUT_MESSAGE, and UNDO_QUOTA_TEMPLATE.
